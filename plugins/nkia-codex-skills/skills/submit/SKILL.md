# Submit — 개발 작업 제출

개발이 완료된 Linear Task 하나를 동료 리뷰와 수동 merge가 가능한 상태로 준비한다.

## 시작 전 읽을 지침

[공통 이슈·Type·증빙 계약](../../references/issue-contract.md)을 먼저 읽고, 다음 동봉 스킬의 지침을 읽는다.

- [ship](../ship/SKILL.md)
- [linear-issue-evidence](../linear-issue-evidence/SKILL.md)
- [linear-issue-validator](../linear-issue-validator/SKILL.md)
- [code-review](../code-review/SKILL.md)
- [commit](../commit/SKILL.md)

각 스킬의 인증, Linear 파싱, 증빙 적절성, 민감정보, git, PR/MR 메타데이터, 재시도, 댓글 이력, 수동 merge 정책을 따른다. 이 스킬은 아래 실행 순서와 책임 경계만 변경한다. 기존 정책과 아래 예외가 충돌하면 이번 실행에는 아래 예외를 우선한다. 기존 스킬 파일은 수정하지 않는다.

커밋 생성과 코드리뷰의 브랜치·커밋 규칙 검사는 해당 저장소의 최신 개발 가이드 정본을 먼저 확인한다. 저장소 정본과 기존 스킬의 예시·정규식이 다르면 정본을 우선한다. 특히 `lucida-next`는 `docs/05-개발가이드/`에서 현재 규칙을 확인하며, 한글 또는 영문 접두사를 고정 가정하지 않는다.

Linear 검증 댓글, PR/MR 본문, PR/MR 코드리뷰 댓글 작성 전에 [출력 템플릿](references/templates.md)을 읽는다.

## 필수 경계

- PR/MR을 merge하거나 approve하지 않는다.
- `finish`를 호출하거나 이슈를 `Done`으로 전환하지 않는다.
- 스토리 포인트는 산정·입력하지 않고 기존 값을 보존한다. 별도 팀장 AC 승인이나 `[AC 확인]`을 제출 조건으로 요구하지 않는다. AC 충족 검증과 범위 밖 변경의 사용자 승인 절차는 그대로 유지한다.
- 증빙·검증 단계에서 PR/MR이나 선행 코드리뷰 결과를 요구하지 않는다.
- 기존 evidence·validator 스킬을 하위 워크플로로 호출하지 않는다. 충돌하지 않는 기존 정책을 push된 commit SHA 기준으로 직접 적용한다.
- 검증 단계는 AC 결과 판정을, 코드리뷰 단계는 구현 위험 검토를 담당한다. 서로의 판정을 반복하지 않는다.
- 기능 AC 중 실패·미검증·증빙 부족이 있으면 `In Review` 전환 전에 중단한다.
- 리뷰 수정 반복 중에는 `In Review`를 유지한다. 최신 검증 실패를 명확히 보고하고 상태를 자동으로 되돌리지 않는다.

## 목표 등록과 진행 유지

`submit` 실행 시 작업을 식별한 뒤 다음 완료 조건과 단계별 진행을 작업 계획에 기록한다. 별도 Goal 생성은 사용자가 명시적으로 요청한 경우에만 수행한다. 일반 제출 요청을 Goal 생성 요청으로 해석하지 않는다.

> 대상 Linear 작업의 구현과 증빙을 검증하고 코드리뷰를 통과해 수동 병합 대기 상태로 준비한다.

- Codex·Claude의 기능이 같다고 가정하지 않는다. 현재 환경에서 실제 제공하는 도구와 상태 규칙을 확인해 사용한다. 목표 기능이 없으면 사용 가능한 작업 계획에 같은 목표와 단계별 진행 상태를 기록한다.
- 같은 작업의 활성 목표가 있으면 재사용한다. 다른 작업의 목표를 덮어쓰거나 완료 처리하지 않는다. 목표 예산은 사용자가 지정한 경우에만 설정한다.
- 각 단계가 끝날 때 완료 단계, 현재 단계, 다음 조치, 검증한 commit SHA, 증빙·댓글·PR/MR 링크, 재시도 횟수를 작업 추적 기록에 남긴다. 이 기록을 이슈 AC에 추가하지 않는다.
- 중단 후 재개하거나 대화 맥락이 축약되면 기록을 읽고 실제 Git·Linear·PR/MR 상태를 다시 확인한다. 완료된 쓰기 작업을 중복 실행하지 않으며 SHA가 달라졌으면 필요한 재검증 단계로 돌아간다.
- 사용자 확인을 기다린 뒤 `적용`, `진행`, `넘어가` 등의 답변을 받으면 기존 작업 기록을 읽고, Goal을 사용 중인 경우에만 그 상태를 조회한다. 승인된 조치와 해소된 대기 사유를 기록하고, 목표가 활성 상태인지 확인한다. 이미 활성 상태이면 같은 목표로 계속한다.
- 목표가 일시정지·정체·차단 상태이면 해당 환경이 제공하는 정식 재개 기능을 사용한 뒤 상태를 다시 조회한다. 재개 기능이 없으면 목표를 재개했다고 표현하지 않는다. UI에서 재개가 필요한 사실을 알리고, 이미 승인된 작업은 작업 계획으로 추적하며 계속한다. 기존 목표를 완료 처리하거나 새 목표로 바꾸어 재개를 흉내 내지 않는다. Codex의 `update_goal`은 재개 도구가 아니므로 재개 용도로 호출하지 않는다.
- 사용자 응답 대기를 목표 실패로 취급하지 않는다. 차단 상태는 실제 사용 중인 도구의 조건을 만족할 때만 설정하며, 단순 확인 대기 때문에 성급하게 차단으로 전환하지 않는다.
- 승인된 범위에서 안전하게 해결 가능한 실패는 기존 재시도 한도 안에서 수정·재검증한다. 중간 단계 성공만으로 전체 작업을 완료 처리하지 않는다.
- 필수 검증 실패는 후속 단계 진입을 막는다. 해결 가능한 항목을 처리한 뒤에도 권한·도구·자료 부족, 재시도 한도, 사용자 판단 때문에 진행할 수 없으면 원인·남은 작업·재개 지점을 기록하고 보고한다. 목표를 완료로 표시하지 않으며, 차단 상태 전환은 해당 도구의 조건을 따른다.
- 아래 완료 조건을 모두 확인한 뒤 작업 계획을 완료 처리한다. Goal을 사용 중이면 도구의 완료 조건에 따라 완료 처리한다. 목표의 끝은 수동 merge 대기이며, 동료 리뷰나 실제 merge를 기다리는 동안 목표를 계속 실행하지 않는다.
- 목표 등록은 기존 승인 범위와 재시도 한도를 넓히지 않는다. 이 스킬을 작성·수정·설명하는 요청에서는 제출 목표를 실제로 시작하지 않는다.

## 실행 절차

### 1. 작업과 Git 범위 확인

1. 사용자 입력, 브랜치, 커밋 또는 저장소 맥락에서 Linear Task를 식별한다.
2. Task의 AC, 범위, 현재 상태를 읽고 부모 Feature가 있으면 함께 읽는다.
3. 현재 브랜치의 변경과 이슈 범위를 대조한다. AC에 없는 추가 개발·수정은 증빙 단계의 사용자 확인 절차로 넘긴다. 대상 브랜치가 불명확하면 중단한다.
4. 현재 저장소 정책에 따라 실제 통합 대상 브랜치를 결정한다.

### 2. 필요한 commit·push 수행

1. staged·unstaged·untracked 변경을 확인한다.
2. 미커밋 변경이 있으면 기존 commit 워크플로에 따라 작업 단위로 커밋한다.
3. 의도한 커밋이 이미 있으면 빈 커밋이나 중복 커밋을 만들지 않는다.
4. 현재 브랜치의 head가 원격에 없으면 push한다.
5. push된 전체 commit SHA를 기록한다. PR 생성 전 증빙과 검증은 이 SHA에 연결한다.

### 3. 증빙 단계 — Evidence Gate

#### 추가 개발·수정의 AC 편입

증빙 수집 전에 현재 작업의 전체 변경을 이슈의 AC·범위와 대조한다. 기존 AC에 포함되지 않은 추가 동작이나 수정 결과가 있으면 다음 절차를 따른다. 기존 AC를 구현하기 위한 내부 부수 변경마다 별도 AC를 만들지는 않는다.

1. 추가 변경의 목적·사용자 영향, 기존 범위와의 차이, 추가할 결과 중심 AC 문구를 모아 사용자에게 보여준다. 원래 범위 밖의 변경이면 그 사실도 명시한다.
2. 해당 변경을 이번 이슈의 AC에 추가할지 사용자에게 묻고 답을 기다린다(HITL). 이미 같은 변경과 AC 편입을 명시적으로 승인한 기록이 있으면 이를 사용하고 다시 묻지 않는다. 코드가 존재하거나 개발을 요청했다는 사실만으로 AC 편입 승인으로 간주하지 않는다.
3. 승인되면 기존 AC ID·본문·체크 상태를 보존하고 새 AC를 미체크 상태로 추가한다. 범위가 확장됐다면 포함·제외 범위도 승인 내용에 맞게 갱신한다. 사용자 동의 없이 별도 이슈로 분리하거나 변경을 삭제하지 않는다.
4. 승인 일시, 승인한 추가 변경, 새 AC ID, 범위 변경 내용을 Linear 검증 댓글의 이력에 기록한다. 이슈를 다시 조회해 저장 성공을 확인한 뒤 새 AC까지 증빙 수집·검증을 계속한다.
5. 사용자가 편입을 거절했거나 답변이 없으면 해당 변경을 승인된 범위로 취급하지 않는다. 분리 또는 제외 방법을 사용자와 정하기 전에는 제출을 완료하지 않는다.

사용자가 승인한 추가 AC와 범위는 이후 검증의 기준이다. 기존 범위 밖이었다는 이유만으로 다시 실패 처리하지 않는다. 승인은 기록된 변경에만 적용하며, 이후 별도 추가 변경까지 포괄하는 예외로 사용하지 않는다. 승인 기록은 범위 판단의 근거이며 구현 완료 증빙이 아니다. 새 AC도 동일한 증빙·검증 기준을 통과해야 한다.

#### 증빙 수집

테스트는 AC와 변경 코드의 호출부·의존 관계에서 도출한 영향 범위로 선택한다. 먼저 실행할 테스트와 해당 AC·회귀 위험의 연결을 간단히 기록하고, 관련 테스트 파일·테스트명·패키지부터 실행한다. 기존 참고 문서의 `go test ./...`, `npm test` 같은 예시를 전체 실행 지시로 해석하지 않는다.

- 서비스 전체 또는 저장소 전체 테스트는 저장소 필수 검사, 사용자의 명시적 요청, 공통 기반 변경으로 인한 광범위한 영향 등 구체적인 근거가 있을 때만 실행하고 이유를 기록한다. 관련 검사가 통과했고 새로운 위험이 없으면 범위를 계속 넓히지 않는다.
- 실패한 테스트 파일이 diff에 없다는 이유만으로 기존 기준선 실패라고 단정하지 않는다. 동일 환경의 변경 전 기준 commit 재현 결과나 해당 commit의 신뢰할 수 있는 CI 결과로 확인한다. 확인하지 못하면 `기준선 여부 미확인`으로 기록하고 변경 코드와 실패 경로의 연관성을 조사한다.
- 실행한 범위·명령·commit·결과와 미실행 범위를 구분한다. 컴파일만 성공하거나 `no tests to run`인 결과를 테스트 통과로 계산하지 않는다.

기능 AC를 판정하는 데 필요한 최소 증빙을 수집한다.

- 대상·방법·통과/실패 수·통과율을 포함한 테스트 결과. 미실행 항목이 있으면 그 수도 기록한다.
- 화면 동작을 보여주는 UI 스크린샷.
- AC에서 요구하는 API 응답, 애플리케이션 로그, DB 조회 결과, 지표, 문서 또는 보고서.
- push된 commit SHA와 브랜치.

적용 규칙:

- 영상은 증빙 수집·등록 대상에서 제외한다.
- 증빙마다 하나 이상의 AC ID를 연결한다.
- 증빙 내용을 실제로 확인한다. 접속 가능 여부만으로 판단하지 않는다.
- 코드 diff만으로 실행 동작을 증명하지 않는다.
- 비밀정보, 토큰, 비밀번호, 개인정보와 안전하지 않은 원본 로그를 제외한다.
- 기존 증빙 미리보기 정책에 따라 Linear resource·attachment와 체크박스 변경 예정 내용을 저장 전에 보여준다.
- 여러 AC에서 사용하는 증빙은 한 번 저장하고 해당 AC에서 참조한다.
- AC 아래 `증빙 예정:`의 자료·확인 내용을 기준으로 수집한다. 저장·내용 확인 후 같은 불릿을 `증빙: 실제 링크·결과`로 교체하며 예정 안내를 중복해서 남기지 않는다. 일부만 확보했으면 확보분과 미확보 예정 자료를 구분하고 AC를 미체크로 유지한다. `증빙 예정:` 자체는 완료 근거가 아니며 필수 자료가 남으면 Validation Gate를 통과시키지 않는다. 재검증은 같은 증빙 불릿을 갱신하고 이전 이력은 보존한다.
- 장문 설계서·보고서·로그는 이슈 Resources → Add document에 해당하는 `save_document(issue, title, content)`로 저장하고 재조회한 document URL을 링크한다. 파일 attachment·GitHub blob 링크로 대신하지 않는다. 짧은 결과·로그는 AC 아래 증빙 불릿에 실제 출력을 코드 블록으로 직접 넣는다. 이미지·바이너리는 attachment를 사용하며 개인 private 저장소 링크로 팀 공유 증빙을 대신하지 않는다.
- 위 저장 위치 기준으로 실제 내용을 확인한 후 대상 AC 아래에 `증빙: [자료](실제 URL) · 대상·방법·통과/실패 수·통과율` 요약을 표시하고, 화면 자체가 필요한 경우 대표 이미지를 inline 표시한다. 긴 로그는 document 링크로, 반복 이미지는 attachment 링크로 분리한다. 재검증은 기존 요약을 갱신하고 이전 실패·증빙 링크·해소 이력은 검증 댓글에 보존한다. 쓰기 직전 최신 본문을 읽고 다른 AC·사용자 편집을 보존한다. 자료를 확인하지 못하면 체크하지 않는다.
- 비 PR 원본 자료는 이슈당 최대 5개이며 이전 자료도 포함한다. 동일 원본은 한 번 저장하고 여러 AC에서 참조한다. 제목은 `[AC-01, AC-02] 대상 — 방법 — 결과`로 지정한다. 초과하면 기존 이력을 보존하는 합본 등으로 정리하며 임의 삭제하지 않는다. 기존 형식에는 소급하지 않는다.
- PR/MR 링크를 요구하거나 만들어내지 않는다.
- 이 단계는 사실을 기록하며 AC의 최종 판정을 내리지 않는다.

### 4. 검증 단계와 In Review 전환 — Validation Gate

수집한 증빙으로 모든 기능 AC를 검증한다. 기능 AC는 제품·시스템·문서·연구·평가 결과를 설명하는 조건이다. `코드 리뷰 완료`, `PR/MR 생성`, `merge 완료` 같은 개발 제출 절차 AC는 모든 단계에서 무시한다. 증빙 수집, PASS/FAIL 판정, 통과율 분모, 상태 전환 조건, 체크박스 갱신에 포함하지 않는다. 기존 절차 AC 문구와 체크 상태는 그대로 보존한다. 실제 제품 결과인 배포·문서 게시 등을 이름만 보고 절차 AC로 제외하지 않는다.

기능 AC가 0개이면 이슈 정의 보완이 필요한 FAIL로 처리한다. AC 아래 실제 출력과 링크된 document·attachment 내용을 확인하며 요약만으로 PASS하지 않는다.

기능 AC마다 다음을 수행한다.

1. 코드와 실행 증빙을 함께 확인해 AC에서 요구한 동작과 결과가 올바르게 구현됐는지 판단한다. 코드 변경이 없는 작업은 문서·분석·측정 결과 등 해당 결과물을 확인한다.
2. 확인한 코드와 증빙이 현재 commit SHA에 해당하는지 확인한다. 실행 동작을 요구하는 AC는 코드만으로 통과시키지 않고 테스트·화면·API 응답 등 실행 결과로 검증한다.
3. AC 충족을 직접 확인할 수 있을 때만 `PASS`로 판정한다. 구현 오류·미검증·증빙 부족이 있으면 원인·영향·필요 조치를 적고 `FAIL`로 판정한다.
4. 일부 항목이 실패해도 나머지 AC 검증을 계속한다.

판정 후 처리:

- 기능 AC 체크박스만 갱신한다.
- 새 템플릿으로 Linear 검증 댓글 하나를 생성하거나 갱신하고 이력을 보존한다.
- 검증한 commit SHA를 기록한다.
- 모든 기능 AC가 통과하고 검증 댓글 저장이 성공했을 때만 Task를 `In Review`로 전환한다.
- 코드 확인 범위는 AC 구현 판정에 필요한 부분으로 한정한다. AC에 보안·성능 조건이 있으면 해당 조건도 검증한다. 코드 전반의 품질·보안·성능·유지보수성과 AC에 명시되지 않은 경계 조건·회귀·병합 위험은 코드리뷰 단계에서 검토한다.

### 5. PR/MR 생성

검증 단계가 PASS이면 다음을 수행한다.

1. 로컬 head, 원격 head, 검증한 SHA가 같은지 확인한다.
2. 기존 ship의 메타데이터·본문 정책과 새 템플릿을 적용해 통합 대상 브랜치로 PR/MR을 Draft 상태로 생성한다. GitHub는 `gh pr create --draft`, GitLab은 해당 환경의 Draft 생성 기능을 사용하고 저장 상태를 재조회한다. 같은 작업의 PR/MR이 이미 있으면 재사용한다.
3. 기존 ship 정책에 따라 담당자를 지정한다.
4. PR/MR 생성 또는 기존 PR/MR 재사용 직후 대상 Linear 이슈를 조회하고, 같은 URL이 없으면 `save_issue(id=이슈 ID, links=[{title: PR/MR 제목, url: 실제 PR/MR URL}])`로 직접 연결한다. GitHub/GitLab 훅·자동 연동 유무와 관계없이 수행하며, 이미 연결되어 있으면 중복 등록하지 않는다. 저장 후 이슈 attachments에서 URL을 재조회한다. 실패하면 연결 미완료로 보고하고 제출 완료로 처리하지 않는다. 이 작업을 위해 훅·저장소 권한·통합 설정을 변경하지 않는다. 링크 등록은 PR 상태 자동 동기화·머지 시 이슈 자동 전환·Linear 내 코드 열람을 보장하지 않는다. 이슈 없는 standalone 작업에는 새 이슈를 만들지 않고 N/A로 기록한다.
5. Codex 앱에서 PR 생성·갱신 작업 시 PR URL을 작업에 연결하는 도구가 제공되면 연결한다.
6. head와 검증한 SHA가 다르면 PR 생성이나 리뷰를 진행하지 않고 영향받는 단계로 돌아간다.

### 6. 코드리뷰 단계 — Code Review Gate

PR/MR에 기존 `nkia-codex-skills:code-review` 전체 워크플로를 적용하되 다음 책임 경계를 따른다.

- base부터 head까지 전체 diff를 대상으로 구현 결함·보안·성능·오류 처리·호환성·회귀 위험, 브랜치·커밋 규칙, 충돌 상태와 병합 가능성을 검토한다.
- Linear는 작업 범위 이탈 확인에만 사용한다. 기능 AC를 재판정하거나 Linear 검증 판정을 대체하지 않는다.
- 범위 이탈은 사용자 승인으로 갱신된 최신 AC·범위를 기준으로 판단한다. 승인된 추가 변경은 원래 범위를 벗어났다는 이유로 finding이나 FAIL로 처리하지 않는다. 승인 기록과 변경의 대응을 확인하고, 승인되지 않은 추가 변경은 증빙 단계의 사용자 확인 절차로 돌린다. 범위 승인은 보안·품질·회귀 위험 검토를 면제하지 않는다.
- 실행 테스트가 통과해도 코드 위험을 무시하지 않는다. diff에 문제가 없어도 실행 AC 증빙을 대신할 수 없다.
- `PR/MR 코드리뷰 댓글` 템플릿으로 댓글을 작성하거나 갱신한다. `submit` 실행에서는 기존 사람이 읽는 댓글 배치를 이 템플릿으로 대체한다. 제목, 본문의 전체 판정·상세 지적·차단 사유, 이력, 댓글 갱신, 검토 완전성, 신뢰도, 수동 merge 규칙은 유지한다.

현재 head SHA의 본문 판정이 없거나, PASS와 수정 지적이 충돌하거나, 검토 차단이면 통과로 간주하지 않는다. 기존 댓글의 승인·승인 가능 문구도 동일한 안전 조건으로 읽고 기계용 블록만 있는 댓글은 재리뷰한다.

PR/MR 본문이 현재 head의 변경 요약·검증 commit·기능 AC 수·검증 결과를 반영하지 않으면 리뷰를 통과로 간주하지 않는다. 본문을 먼저 갱신하고 재조회로 저장을 확인한 뒤 리뷰 판정을 내린다.

### 7. 수정·재검증 반복

안전하게 수정 가능한 리뷰 지적은 수정 후 새 커밋을 만들고 push한다. 변경 영향에 따라 다음 단계로 돌아간다. 새 커밋이 생기면 코드리뷰(재리뷰)로 돌아가기 전에 PR/MR 본문의 변경 요약·검증 commit·기능 AC 수·검증 결과를 현재 head 기준으로 점검·갱신한다. 승인으로 편입된 AC나 새 변경 섹션도 본문에 반영한다.

| 변경 내용 | 다시 수행할 단계 |
|---|---|
| 동작·테스트·AC 결과 변경 | 증빙, 검증, 코드리뷰 |
| 오류 처리·보안·성능·리팩터링 변경 | 영향받는 테스트 증빙을 갱신한 뒤 검증, 코드리뷰 |
| 대상 브랜치 충돌 해결 | 코드리뷰. 동작이나 테스트가 달라질 수 있으면 증빙부터 수행 |
| PR/MR 문구·메타데이터만 변경 | PR/MR 메타데이터 확인만 수행 |

영향이 불명확하면 증빙 단계부터 다시 수행한다. 이전 SHA의 PASS를 재사용하지 않는다. 자동 수정·재리뷰는 최대 3회이며 기존 코드리뷰 제한이 더 작으면 그 한도를 따르고, 수정에 사람의 판단이 필요하면 중단한다.

코드리뷰 자체는 절차 AC 존재 여부와 관계없이 수행하며 절차 AC는 체크하지 않는다.

### 8. Draft 해제와 수동 병합 대기

- 리뷰 댓글 제목은 `# MR 코드 리뷰 결과 ⚠️` 또는 `# MR 코드 리뷰 결과 ✅`으로 작성한다. 제목에는 상태 설명 문구나 구분선을 덧붙이지 않는다. ✅는 머지 가능, ⚠️는 사용자 점검이 필요한 상태를 뜻한다. 검사 진행 중·차단·실패 등 구체적 이유는 본문에 적는다. 기존 제목 접두사는 유지한다.
- 현재 head SHA의 기능 AC PASS, 코드리뷰 `PASS`와 Critical 0·Warning 0, 충돌 없음, 필수 CI 통과를 확인한 뒤 Draft를 해제한다. 필수 CI가 없으면 없음으로 기록한다. 상태 미확인·검사 진행 중·실패가 있으면 Draft와 대기 표시를 유지하고 이유를 적는다.
- GitHub는 `gh pr ready`, GitLab은 해당 환경의 Ready 전환 기능을 사용한다. Draft 자체가 원인인 병합 차단은 해제 전 실패로 취급하지 않는다. 실제 approve·merge는 수행하지 않는다.
- 해제 후 Draft 상태·head SHA·병합 조건을 재조회하고 성공했을 때만 댓글 제목을 `✅`으로 갱신한다. 해제 실패는 `⚠️`로 남긴다. 머지 가능은 자동 검증 완료와 수동 병합 대기를 뜻하며 동료 승인이나 보호 규칙을 우회하지 않는다.
- 새 코드 변경으로 기존 판정이 유효하지 않게 되면 작업 소유의 열린 PR/MR을 Draft로 되돌리고 제목도 `⚠️`로 갱신한 뒤 재검증한다.
- 필요에 따라 Linear resource를 갱신하고 PR/MR URL, 검증한 SHA, 리뷰 판정, 남은 지적과 수동 merge 필요 여부(`manual merge required`)를 보고한다.

## 완료 조건

다음 조건을 모두 만족해야 제출 준비 완료로 종료한다.

- 현재 PR/MR head SHA에 대해 모든 기능 AC가 PASS다.
- Task 상태가 `In Review`다.
- PR/MR이 존재하고 Linear에 연결되어 있다.
- PR/MR의 Draft가 해제됐고 필수 CI가 통과했거나 필수 CI가 없음을 확인했다.
- 코드리뷰가 `PASS`이며 Critical 0, Warning 0이다.
- 보고된 merge 충돌이 없다.
- 사용자 또는 동료가 수동으로 merge할 수 있다.
