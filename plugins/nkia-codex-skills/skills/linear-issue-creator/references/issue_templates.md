# 작업 유형별 입력 가이드

[공통 계약](../../../references/issue-contract.md)의 4절 본문·Type 선택·AC 규칙을 적용한다. 아래는 입력 시 확인할 내용이며 별도 본문 절을 늘리는 템플릿이 아니다.

| 작업 | 확인할 내용 | 결과 중심 AC 예 |
|---|---|---|
| 빌드·배포 | 대상 환경, 버전, 배포·복구 범위 | 대상 환경에서 지정 버전이 실행되고 상태 확인이 정상이다 |
| 데이터 | 데이터 목적, 소스, 건수·품질·처리 범위 | 지정 건수와 품질 기준을 만족하는 데이터를 조회할 수 있다 |
| Evaluation | 비교 대상, 기준, 측정 방법 | 같은 조건의 측정 결과와 적합성 판정이 재현된다 |
| Feature | 사용자 시나리오, 입력·출력, 경계 | 새로운 기능의 정상·실패 흐름을 사용자가 확인할 수 있다 |
| Improvement | 현재 문제, 기준값, 기대 개선 | 합의한 품질·성능·사용성 기준을 충족한다 |
| Refactoring | 보존할 동작, 변경 범위 | 영향받는 정상·경계 동작이 변경 전과 동일하다 |
| Research | 학술 질문·가설, 방법론 | 연구 질문에 대한 결과와 근거·한계를 제시한다 |
| Investigation | 결정할 사항, 대안, 적용 조건 | 대안 비교와 선택 근거·제약을 제시한다 |
| Bug | 재현 조건, 기대·실제 동작 | 재현 조건에서 기대 동작을 만족하고 인접 경로가 회귀하지 않는다 |
| Documentation | 독자, 문서 목적, 게시 범위 | 독자가 문서 절차로 요구한 작업을 수행할 수 있다 |
| Task | 운영·지원 목적, 대상·완료 결과 | 합의한 운영·지원 결과를 확인할 수 있다 |

- AC 수와 수치 기준은 작업에 맞게 정한다. 미정 기준을 임의 숫자로 채우지 않는다.
- 데이터 작업은 목적에 따라 Type을 결정한다. 평가를 Research, 리팩터링을 Feature, 문서를 Task로 치환하지 않는다.
- PR·코드리뷰·merge는 공통 AC로 추가하지 않는다. 문서 검토 자체가 요구 결과인 경우는 보존한다.
- 생성 단계에서 각 AC 아래에 `증빙 예정: 자료 종류·확인할 내용` 불릿을 작성한다. 증빙 게이트에서 자료 확인 후 같은 불릿을 `증빙: 실제 링크·결과`로 교체한다. 가짜 URL·실행 결과는 작성하지 않는다.
- 제목은 무엇을 왜 바꾸는지 표현한다. 여러 대상을 다루면 공통 목적을 제목으로 하고 구체적인 대상은 범위에 보존한다.
