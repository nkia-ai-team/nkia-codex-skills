# 설명 밀도와 형식 예시

가상의 예시다. 실제 문서의 상태·수치·정책으로 재사용하지 않는다.

## 불릿으로 동작과 이유 분리

Before: “state가 overwrite라 최초 prepend만 하면 소실. 매 턴 entry에서 주입.”

After:

- **처리:** 매 대화 턴 시작 시 참고 정보를 메시지 앞에 추가한다.
- **이유:** 메시지 상태가 덮어써져, 처음에만 추가하면 다음 턴부터 사라진다.

짧게 줄이는 대신 필요한 이유를 풀어 쓰고 훑어보기 쉽게 나눈다.

## 측정 결과와 판정 구분

Before: “평균 0.4초, 최대 0.6초. 응답 시간 0.5초 미만 기준 PASS.”

After:

- **관측:** 평균 0.4초, 최대 0.6초였다.
- **판단:** 평균 기준이면 충족하지만 모든 요청 기준이면 충족하지 못한다. 어떤 통계량으로 판정하는지 확인해야 한다.

수치의 뜻을 보존하고 모호한 판정을 새 정책으로 확정하지 않는다.

## 짧은 변경은 짧게 유지

입력: “설정 화면의 저장 버튼 문구를 ‘확인’에서 ‘저장’으로 변경했다. 기능 변경은 없다. 변경 기록으로 써줘.”

출력:

# 설정 화면 저장 버튼 문구 변경

- **변경:** 버튼 문구를 ‘확인’에서 ‘저장’으로 바꿨다.
- **영향:** 기능 변경은 없다.

원인·테스트·후속 작업을 추측해서 채우거나 빈 절을 추가하지 않는다.

## 좋은 설명은 유지

“특정 동작 자체에는 보상하지 않는다. 그렇지 않으면 해당 동작만 반복해 보상을 얻을 수 있다.”

결정과 이유가 이미 연결되어 있다. 별도의 불릿·표·마지막 요약을 강제하지 않는다.

## 결과 보고는 작업 회고를 줄이기

Before: “검토 과정에서 다음 개선 지점을 정리했다. 배경·세부 설명 사이에서 현재 상태와 결론을 찾아야 했다. 문서 작성 규칙을 개정하고 두 저장소에 스킬을 추가했다.”

After:

- **문제:** 긴 배경 설명에 핵심이 묻힘
- **완료:** 문서 작성 규칙 개정, 두 저장소에 작성 스킬 추가

내용 없는 도입을 삭제하고 문제와 결과를 직접 제시한다. 같은 완료 내용을 개요·진행 과정·결과물에서 반복하지 않는다. 실제 비교·검증을 요구받으면 해당 근거는 남긴다.

## 강의식 표현을 내용 중심으로 바꾸기

| Before | After |
| --- | --- |
| 먼저 알아둘 결론 | 주요 결과 |
| 그룹은 어떻게 나뉘는가 | 그룹 분할 기준 |
| 이 관계가 있으면 함께 검토할 자격이 생긴다. | 직접 연결이 있으면 그룹화 후보 조건 충족 |
| 시간이 겹치면 가장 강하게 시작한다. | 발생 시간이 겹칠 때 관계 가중치 최대 |
| 모든 환경에서 성공한다고 설명하면 안 된다. | 검증 범위: 테스트 환경. 고객 환경 전체의 성능은 미확인 |

어미만 줄이지 말고 실제 조건과 범위를 보존한다. 초보자용 설명·발표 대본·FAQ가 요청됐으면 친절한 설명이나 질문형 제목을 사용할 수 있다.

## 결과 보고와 상세 설명 구분

입력: “그룹화 개선 결과를 팀에 공유할 보고서로 정리해줘. 검증은 저장된 테스트 데이터 10건, 성공 5건에서 8건으로 개선. 운영 환경은 아직 미검증. 알고리즘 설명과 구현 파일 목록도 자료에 있음.”

도입 예시:

- **결과:** 테스트 데이터의 그룹화 성공 5/10 → 8/10
- **검증 범위:** 저장된 테스트 데이터 10건
- **남은 확인:** 운영 환경 검증

이후 변경 내용과 평가 조건·근거를 설명한다. 상세 알고리즘과 구현 위치는 관련 자료로 연결하고, 링크를 확보하지 못했으면 그 상태를 명시한다. “이 문서를 발표하는 순서”나 같은 수치의 마지막 요약은 추가하지 않는다.

사용자가 상세 알고리즘까지 한 문서에 요청했다면 상세 절에 보존한다. 단순히 짧게 만들기 위해 검증 범위나 미완료 상태를 삭제하지 않는다.

## 제목 수정에 그치지 않고 본문 재구성

성과 수치만 빠르게 확인하는 현황 보고의 기존 순서가 ‘요약 → 입력 필드 → 알고리즘 → 수명주기 → 평가 결과’라면, 요약을 불릿으로 바꾸는 것만으로는 부족하다. ‘평가 결과 → 주요 변경 → 검증·한계 → 상세 동작’처럼 본문 순서도 조정한다. 구체적인 순서는 사용자의 목적에 맞춘다.

Before: “20초는 요청이 처음 들어온 뒤 재는 시간이 아니다. 엔진 시작 시 한 번 수집하고, 이후 요청 유무와 관계없이 20초마다 수집한다.”

After:

- **최초 수집:** 엔진 시작 시
- **수집 주기:** 이후 20초마다
- **조건:** 요청 유무와 무관하게 실행

위 시간은 가상 예시다. 실제 문서에서는 원문의 값을 유지한다. 수집 이유·예외가 있었다면 별도 항목이나 필요한 설명 문장으로 보존한다.

검토 시에는 결과가 앞에 있는지뿐 아니라 본문의 복합 문단이 실제로 정리됐는지 확인한다. 표·도표·수치의 보존 검사는 편집 정확성 확인이며, 독자 사용성 평가를 대신하지 않는다.

## 완료 리뷰는 방법을 이해한 뒤 결과 판단

요청: “완료 리뷰에서 기존 문제, 개선 정책·알고리즘, 검증 결과를 설명하고 싶다.”

- 적절한 흐름: 기존 문제 → 개선 방법·입력 관계 → 정책·알고리즘과 사례 → 결과·한계
- 피할 흐름: 성과 표 → 결과 검증 → 뒤쪽 부록에 모든 정책·알고리즘 배치
- 관계 기반 기능이라면 어떤 데이터로 연결을 만들고, 어느 시점의 연결을 쓰며, 그 연결이 최종 판단에 어떻게 영향을 주는지 설명한다. 알고리즘 이름·설정값만 나열하지 않는다.
- 짧은 결과 요약은 허용하되, 방법과 정책을 본문에서 제거하지 않는다. 반대로 주간 현황만 요청받으면 알고리즘 강의를 추가하지 않는다.

가로로 긴 흐름도를 넣어 글자가 작아졌다면, 확대 링크만 추가하지 말고 전체 흐름과 부분 흐름을 나누거나 세로로 재배치한다. 원문 도표를 보존했다는 사실과 독자가 읽을 수 있다는 판단은 별도로 확인한다.
