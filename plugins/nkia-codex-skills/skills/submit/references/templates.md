# Submit 출력 템플릿

`submit`이 작성하는 결과물에는 아래 템플릿을 사용한다. 기존 결과를 갱신할 때는 댓글 ID와 이력을 보존한다.

사람이 읽는 판정은 `✅ PASS`, `❌ FAIL`, `➖ N/A`로 표시한다. 미검증·차단·제약 설명에는 `⚠️`를 사용하되 미검증을 PASS로 표시하지 않는다. 아래 템플릿의 선택지는 실제 결과 하나로 치환한다. 별도 기계용 판정 블록은 쓰지 않는다.

표 안의 판정은 이모지와 텍스트 사이에 줄바꿈 없는 공백(U+00A0)을 사용한다: `✅ PASS`, `❌ FAIL`, `➖ N/A`. 일반 공백으로 바꾸거나 `<br>`를 넣지 않는다. 좁은 결과 열에서 이모지와 판정이 두 줄로 분리되는 것을 방지한다.

## 댓글 문체

- 짧고 쉬운 문장으로 실제 변경·검증 결과만 적는다. 같은 내용을 판정·표·상세에 반복하지 않는다.
- `리뷰 결과`에는 판정과 남은 지적 수만 적는다. 상세에는 지적과 필요한 판단 근거만 남기며 별도 `확인 사항` 제목을 추가하지 않는다.
- 내부 API 용어 대신 독자가 보는 대상·기능 이름을 쓴다. 예: `issue parent` 대신 `해당 이슈의 Resources → Add document`.
- 삭제·유지·미지원 사실을 직접 적는다. `혼동하지 않습니다`, `제거로 이어지지 않습니다` 같은 간접 설명은 쓰지 않는다. 서로 다른 절차를 불필요하게 연결하지 않는다.
- 검증한 경로와 관련된 미검증 경로를 구분한다. 로컬 스킬 사용 검증을 설치 미검증 때문에 누락하지 않으며, 이전 댓글의 제약 목록이나 관계없는 검사를 재사용하지 않는다. 관련 미검증이 없으면 해당 불릿을 생략한다.
- 댓글·문서 ID 재사용 같은 작업 과정은 독자의 판단에 필요한 경우에만 적는다. SHA·판정·지적·차단 사유·검증 근거·기존 이력은 보존한다.

## Linear 검증 댓글

```markdown
# 검증 결과: ✅ PASS | ❌ FAIL

[요구한 결과가 실제로 어떻게 동작하는지 한 문장]

- 검증 commit: `[full SHA]`
- 기능 AC: [통과]/[전체]
- 상태: [현재 Linear 상태]
- 남은 작업: [✅ 없음 또는 ⚠️ 원인·영향·조치]
- 검증: [YYYY-MM-DD HH:mm KST]

## 실제 결과

### 1. [대상]의 [핵심 결과]
- [발생 조건과 관찰 결과]
- [보존된 경계 또는 회귀 결과]

## 실행 검증

- [대상·방법·PASS/FAIL 수·통과율]
- [미실행·기준선 실패·한계]

## 기능 AC 판정 [통과]/[전체]

| AC | 결과 | 근거 |
|---|---|---|
| AC-01 | ✅ PASS | [구현 코드 위치·증빙 링크와 AC 충족 판단] |
| AC-02 | ❌ FAIL | [원인·영향·필요 조치] |

## 검증 히스토리

| # | 일시 | commit | 판정 | 기능 AC | 변화 |
|---|---|---|---|---|---|
| 1 | YYYY-MM-DD HH:mm KST | `[short SHA]` | ✅ PASS/❌ FAIL | 2/2 | [최초 검증 또는 변경점] |
```

작성 규칙:

- 검증 댓글은 하나만 유지하고 재검증 시 갱신한다. 기존 `# ✅ 검증 완료`, `# ⚠️ 검증 실패`, `# ❌ 검증 실패`, `# 검증 결과:`와 기존·새 검증 히스토리 제목을 함께 인식한다. 후보가 여러 개거나 이력 파싱에 실패하면 새 댓글을 만들거나 덮어쓰지 않고 중단한다.
- Linear 댓글에는 `<details>`·`<summary>` HTML을 쓰지 않는다. 실제 화면에서 태그가 그대로 노출된 사례가 있으므로 Markdown 제목과 간결한 표를 사용한다. 접기 기능은 해당 게시 경로에서 실제 렌더링이 확인된 경우에만 도입한다.
- 표의 근거는 짧은 판정 이유와 증빙 링크로 작성하고 긴 코드 경로·로그는 연결된 자료에 둔다.
- 기존 `# 검증 결과:` 제목 접두사를 유지한다. 판정은 접두사 뒤 이모지를 제외한 PASS/FAIL로 읽으며, 기존 이모지 없는 댓글도 같은 댓글로 인식한다.
- 유효한 이력 행을 모두 보존한다.
- 재검증 댓글은 최신 결과 본문 하나와 검증 히스토리 표 하나로 갱신한다. 이전 댓글 전체나 `이전 검증 기록` 아래의 과거 본문을 붙여 넣지 않는다. 기존 이력 행을 모아 같은 표에 새 행을 추가하며, 승인·실패·증빙 상세는 이슈의 검증 document에 보존한 뒤 링크한다. 저장 전후 제목·AC 판정·히스토리 중복과 이력 행 누락을 확인한다. 단순 문구 수정으로 새 검증 이력을 만들지 않는다.
- PR/MR 생성 전에는 PR/MR 리뷰 결과를 포함하지 않는다.
- 증빙 원문을 댓글에 복사하지 않고 저장된 증빙을 링크한다.
- 사용자 승인으로 AC·범위를 추가한 경우 검증 히스토리에 승인 일시·변경 내용·새 AC ID·범위 변경을 남긴다. 이를 AC 통과 증빙으로 대신하지 않는다.

## PR/MR 본문

```markdown
## 1. [제품·화면·서비스]의 [변경 결과]

- 문제: [기존 사용자·운영 문제]
- 결과: [변경 후 관찰 가능한 동작]
- 범위: [포함한 핵심 범위와 제외 범위]

## 검증

- Linear: [이슈 링크]
- 검증 commit: `[full SHA]`
- AC: [통과]/[전체] PASS
- 자동 검증: [대상·방법·PASS/FAIL 수·통과율]
- 통합·시연: [환경과 핵심 결과 또는 미실행]
- 제약: [미검증 범위 또는 없음]
```

서로 다른 리뷰 주제가 있을 때만 번호가 붙은 변경 절을 추가한다. Task를 주된 범위로 삼고 부모 Feature는 배경으로 설명한다.

## PR/MR 코드리뷰 댓글

````markdown
# MR 코드 리뷰 결과 [✅ | ⚠️]

[이 변경을 target branch에 합칠 때의 핵심 판단을 한 문장으로 작성]

- 리뷰 기준: `[head SHA]` · [YYYY-MM-DD HH:mm KST]
- Linear 검증: ✅ PASS · `[validated SHA]`
- 병합 상태: [충돌 없음 | 충돌 있음 | 확인 불가]
- 차단 사유: [없음 또는 원인·필요 조치]

## 리뷰 결과

- 전체 판정: [✅ PASS | ❌ FAIL] · [수동 병합 대기 | 수정 필요 | ⚠️ 검토 차단]
- 남은 지적: Critical [수], Warning [수], Info [수]

## 검토 요약

| 항목 | 결과 | 핵심 근거 |
|---|---|---|
| 브랜치명 | PASS/FAIL | [규칙 일치 여부] |
| 커밋 메시지 | PASS/FAIL | [전체 커밋 검토 결과] |
| 전체 변경 검토 | PASS/FAIL | [base부터 head까지 모든 커밋·파일·대용량 patch 확인 여부] |
| Linear Scope | PASS/FAIL/N/A | [이슈 범위 포함 여부와 범위 밖 변경] |
| 코드 품질 | PASS/FAIL | [결함·오류 처리·구조 일관성·유지보수성] |
| 보안 | PASS/FAIL | [취약점·권한·민감정보 판단] |
| 성능 | PASS/FAIL | [응답 시간·CPU·메모리·조회량·처리량 위험] |
| 테스트 위험 | PASS/FAIL | [변경 경로·경계·회귀를 방어하는 테스트의 충분성] |
| 병합 가능성 | PASS/FAIL | [target branch 충돌·CI·필수 조건] |

## 상세 리뷰

### [변경 목적·동작] — [지적 내용]
- 판정: 수정 필요 | 확인 필요 | 참고
- 위치: `[파일:라인 | 브랜치명 | 커밋 SHA]`[, 관련 위치]
- 이유·영향: [결함 또는 merge 후 발생 가능한 영향]
- 조치: [구체적인 수정 방법 또는 `없음 — 인지 사항`]
- 중요도: Critical | Warning | Info · Confidence: [n]/100 · autofix-safe | manual-required | owner-decision

지적이 없으면 `✅ 지적 없음`으로 작성한다. 필요한 판단 근거만 짧게 덧붙이고 변경 목록을 반복하지 않는다.

## 리뷰 히스토리

| # | 일시 | head | 판정 | 지적 (C/W/I) | 변화 |
|---|---|---|---|---|---|
| 1 | YYYY-MM-DD HH:mm KST | `[short SHA]` | PASS/FAIL | 0/0/0 | [최초 리뷰 또는 변경점] |

## 검증

- 자동: [코드리뷰 중 실행하거나 확인한 검사와 결과]
- 통합·시연: Linear Validation PASS 참조 · `[validated SHA]`
- 병합: [target branch, 충돌 상태, CI 상태]
- 미검증: [이번 변경 판단에 필요한 미검증 경로; 없으면 불릿 생략]

````

작성 규칙:

- `# MR 코드 리뷰 결과`로 시작하는 댓글 하나를 유지한다. 재리뷰 시 새 댓글을 추가하지 않고 기존 댓글을 갱신한다.
- 제목은 모든 자동 검증과 Draft 해제 확인 후 `✅`, 그 전에는 `⚠️`로 표시한다. 대기 사유는 리뷰 결과에 적는다. 제목 접미사가 없던 기존 댓글도 같은 댓글로 인식한다. 제목 아이콘만으로 통과를 판단하지 않고 현재 SHA의 본문 판정·상세 지적·차단 사유를 함께 확인한다.
- 요약 표의 결과는 `✅ PASS`·`❌ FAIL`·`➖ N/A`로 표시한다. 상세 지적의 중요도는 `🔴 Critical`·`🟡 Warning`·`🔵 Info`로 표시한다. 지적이 없으면 `✅ 지적 없음`으로 적는다.
- 검증 항목에는 결과에 맞는 표시를 붙인다. 통과는 `✅`, 실패는 `❌`, 미실행·확인 불가·제약은 `⚠️`로 구분한다. 이모지는 판정과 주의할 사항에 집중하고 모든 문장에 반복하지 않는다.
- 사람용 전체 판정과 이력은 `approved`를 `✅ PASS`, `needs-fix`를 `❌ FAIL`, `blocked`를 `❌ FAIL (⚠️ 검토 차단)`로 표시한다. 과거 영문 판정은 기존 댓글을 읽을 때만 해석하며 새 댓글은 PASS/FAIL로 작성한다. 표시 변경만으로 검토 시각·SHA·판정·이력을 새로 만들거나 갱신하지 않는다.
- 본문 판정이 없거나 상충하거나 현재 SHA와 다르면 통과시키지 않는다. 과거 기계용 블록만 있는 댓글은 재리뷰하며, 갱신 시 블록을 제거하고 기존 이력은 보존한다.
- `PASS`는 Critical 0, Warning 0, 전체 diff 확인 완료, merge 충돌 없음, 필수 검사 차단 없음일 때만 가능하다.
- Linear Scope는 범위 이탈만 확인하고 기능 AC를 재판정하지 않는다.
- 사용자 승인으로 확장된 최신 범위를 기준으로 판단한다. 승인된 추가 변경은 원래 범위를 벗어났다는 이유로 FAIL 처리하지 않고 핵심 근거에 승인 기록을 참조한다.
- `테스트 위험`은 테스트가 변경 코드와 예상 회귀를 방어하는지 검토한다. 실행 결과에 대한 AC 검증은 반복하지 않는다.
- 조치가 필요한 지적은 변경된 줄에 한해 신뢰도 80/100 이상일 때만 작성하며 자동 수정 가능 여부 분류를 포함한다.
- 유효한 이력 행을 모두 보존하고 각 시도의 현재 head SHA를 기록한다.
- 리뷰 히스토리의 지적 열은 `지적 (C/W/I)`로 쓰고, 값은 Critical/Warning/Info 순서의 숫자만 `0/0/0`처럼 표시한다. 기존 숫자·시각·SHA·판정은 형식 수정만으로 바꾸지 않는다.
- 표 헤더·구분선·이력 행 사이에 빈 줄을 넣지 않는다. 저장 후 재조회하고 GitHub에서는 렌더링 HTML로 모든 이력이 같은 표에 포함되는지 확인한다.

## 완료 출력

```text
=== 제출 준비 완료 ===

Linear: {issue-id} — In Review
검증 commit: {full-sha}
PR/MR: {url}
기능 검증: PASS ({passed}/{total})
코드 리뷰: 승인
남은 이슈: Critical 0, Warning 0

수동 merge가 필요합니다.
```
