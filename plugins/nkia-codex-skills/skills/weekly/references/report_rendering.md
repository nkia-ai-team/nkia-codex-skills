# Report Rendering

B/C/D/F/G 열의 업무 표현과 예상 목표일·진척도 산정 기준이다.

## 1. 기능·목표 단위로 업무 묶기

**번호 항목 하나는 사용자에게 제공할 하나의 기능 또는 달성할 목표다.** 실행자 본인의 Linear 이슈, 커밋·미커밋 코드, 작업 기록과 결과물에서 공통 목적을 찾아 묶는다. 이슈가 없어도 실제 작업을 포함한다. 제목만 읽어도 무엇을 제공하거나 해결하려는지 알 수 있는 수준으로 추상화한다.

먼저 목표를 정하고, 그 목표를 위한 **실험·조사·기획·구현·검증은 D열의 작업 내용 불릿**에 배치한다. 각 활동의 진척도가 달라도 같은 기능을 위한 활동이면 하나의 목표로 유지한다. 개별 실험명·실행 횟수·작업 단계의 나열을 업무 제목으로 삼지 않는다.

| 수집된 활동 | 업무 제목 | 작업 내용에 둘 근거 |
|---|---|---|
| KEDB 유사 판별 실험, 증상 중심 그래프 기획 | 증상 기반 장애 사례 탐색 | 판별 방식 비교 결과, 증상 묶음 기준, 그래프 탐색 흐름 |
| 검색 후보 비교, 청킹 조정, 답변 프롬프트 개선 | 문서 기반 질의응답 개선 | 후보 비교, 문서 맥락 보존, 답변 검증 결과 |

`KEDB 고도화 실험 및 증상 중심 그래프 기획`처럼 활동명을 이어 붙이거나, `KEDB`처럼 프로젝트명만 쓰는 제목은 위 기준으로 다시 잡는다. 서로 독립적으로 제공·완료할 수 있는 기능이면 별도 번호 항목으로 나눈다. 조사 자체가 요청된 업무라면 `검색 전략 선정`처럼 의사결정·산출물 목표로 표현한다. 실제 업무에 없는 기능이나 완료 범위를 만들어 묶지 않는다. 이슈 ID·PR 번호는 본문 대신 근거 메모에 둔다.

## 2. B/F열 — 업무구분

기본값은 둘 다 정확히 `백로그`다. 기존 시트 드롭다운 값을 따른다. 투입시간은 계산하거나 기록하지 않는다. 미리보기에서는 두 값이 같으면 `업무구분: 백로그`처럼 한 번만 표시하고, 다르면 금주·차주를 구분한다. 시트에는 각각의 열에 기록한다. `[C]`, `[D]` 같은 열 표시는 미리보기에 노출하지 않는다.

## 3. C열 — 업무명 목록과 D열의 일정·진척도 산정

C열에는 §1에서 정한 기능·목표명만 번호 목록으로 쓴다. 시트의 기존 열 제목에 목표일·진행율이 있더라도 셀 내용에는 날짜·%를 넣지 않는다.

    1. 문서 기반 질의응답 개선
    2. 증상 기반 장애 사례 탐색

날짜·진척도는 아래 기준으로 산정해 D열의 각 목표 제목에만 `(~MM/DD, N%)`로 한 번 표시한다. C/D의 목표명과 번호는 일치시킨다. 목표 아래에 실험·기획·개발별 제목과 날짜·%를 다시 만들지 않는다.

### 진척도: 작성된 완료 조건 없이도 추정

1. Linear 이슈가 있으면 설명·AC·일정을 참고하되, 실제 코드·검증 기록과 함께 판단한다. 이슈 상태만으로 %를 고정하지 않는다.
2. 이슈나 AC가 없으면 작성자 본인의 코드와 미커밋 diff, 연결된 호출 경로·테스트·결과물·작업 대화에서 **현재 하려던 일과 구현된 범위**를 추론한다. 완료 조건을 먼저 작성하라고 요구하거나 산정을 포기하지 않는다.
3. 구현된 핵심 기능과 확인된 결과를 중심으로 10% 단위의 대략적인 값을 제시한다. 코드 줄 수·커밋 수·테스트 성공률을 기계적으로 환산하지 않는다.
4. 아래 단계 기준과 실제 남은 작업으로 판단하며 기본 상향이나 일률적인 가산은 하지 않는다. 두 구간 사이이면 더 높은 단계의 근거가 확인되는지 보고 선택한다. 미커밋 상태나 별도 후속 개선만으로 감점하지 않되, 현재 업무에 속한 미해결 결함·검증은 반영한다.
5. 먼저 기능·목표의 현재 범위를 정하고 그 범위에서 구현·검증된 부분과 남은 부분을 대조해 **목표 전체의 진척도 하나**를 산정한다. 실험·기획·구현의 %를 평균하거나, 높은 %를 만들려고 범위를 완료한 실험이나 일부 구현으로 축소하지 않는다. 미리보기에는 선택한 단계와 실제 잔여 작업을 한 문장으로 설명한다.

| 관찰한 현재 작업 상태 | 대략적인 진척도 참고 |
|---|---|
| 계획만 있고 아직 착수하지 않음 | 0% |
| 방향 탐색·초기 구현 | 20~40% |
| 주요 구현 진행, 핵심 경로 일부 미연결 | 50~70% |
| 핵심 구현 연결, 대표 결과 확인, 보완 진행 | 80% |
| 주요 구현·검증 완료, 작은 보완·최종 확인만 남음 | 90% |
| 업무 제목의 전체 범위에서 구현·필요 검증이 끝나고, 그 범위의 남은 작업이 없다는 근거 확인 | 100% |

표는 고정 점수표가 아니다. 예를 들어 검색 구현·검증을 마쳤다면 별도 Chat 연동까지 포함해 진행률을 낮추지 않는다. 요청된 목표가 전략 선정이라면 비교와 채택/보류 판단까지 마쳤을 때 완료일 수 있다. 그러나 기능 개선 업무를 보고하면서 후보 비교 완료만으로 100%를 주지 않는다. 결과보고서의 “완료” 문구 하나나 테스트 통과만으로 전체 완료를 판정하지 않는다. 반대로 핵심 실행이 실패하는데 코드가 많다는 이유로 90%를 주지 않는다. 배포가 현재 작업에 포함된 경우에만 미배포를 남은 작업으로 센다.

작업 범위 자체를 식별할 자료가 전혀 없으면 구체적인 %를 꾸며내지 않는다. 자료가 있는 상태에서 AC가 없다는 이유만으로 확인 질문을 반복하지 않는다.

### 예상 목표일

- 사용자 명시 일정 → 해당 작업의 기록된 일정 → 실제 남은 작업에 대한 추정 순서로 정한다. 완료 작업에 일정이 없으면 확인된 실제 완료일을 쓴다.
- 일정이 없으면 남은 보완의 크기·의존성·최근 작업 속도로 가장 가까운 현실적인 날짜를 제시한다. 작은 수정·최종 확인만 남았으면 당일이나 다음 업무일도 고려한다. 자동으로 차주 금요일까지 늘리거나 모든 항목에 일률적인 여유를 붙이지 않는다.
- 큰 미해결 결함·외부 대기가 있으면 그 영향을 반영한다. 남은 작업을 알 수 없으면 `목표일 미정`으로 둔다. 과거 목표를 임의로 새 날짜로 덮지 말고 지연/재예상을 구분한다.
- 확정 일정이 아닌 날짜·진척도는 **미리보기의 셀 내용 밖**에 짧게 추정이라고 밝힌다. 업무당 근거 한 문장 정도면 충분하다. 예상일을 실제 약속으로 표현하지 않는다.

## 4. D열 — 업무 내용

각 업무 제목에 `(~MM/DD, N%)`를 붙이고, 아래에 `문제:`와 `작업 내용:`을 분리한다. 문제는 간결하게 설명하고, 수행한 일은 의미 단위로 나열한다. 문장·불릿 수나 시작 동사를 강제하지 않는다. 커밋 메시지나 AC를 그대로 나열하지 말고 중복을 합쳐 실제 업무를 설명한다. 결과 수치는 관련 작업 불릿에 넣는다. `개선/평가 결과/진행 현황` 같은 별도 구획은 기본으로 늘리지 않는다.

```text
1. 문서 검색 개선 (~09/18, 90%)
   문제: 필요한 문서가 검색 상위 결과에서 누락됨.
         표의 항목과 값이 분리되어 검색 근거가 약해짐.

   작업 내용:
   - 문서 형식별 파서 비교 및 표 정보 누락 보완
   - 벡터·키워드 혼합 검색 구현
   - 대표 질문으로 검색 결과 비교 및 최종 회귀 확인

2. 근거 표 가독성 개선 (~09/18, 100%)
   문제: 내부 JSON이 그대로 노출되어 근거를 읽기 어려움.

   작업 내용:
   - 원문을 지표·현재값·정상값 중심의 문장으로 변환
   - 원천 시각이 있는 근거에 시각 표시 추가
   - 대표 화면 확인 및 문서 반영 완료
```

- 번호 블록 사이와 `문제:`/`작업 내용:` 사이에 빈 줄을 둔다. 긴 문제 문장만 의미 단위로 줄을 바꾸고, 이어지는 줄은 본문 시작 위치에 맞춘다. 하위 불릿은 같은 깊이로 들여쓴다.
- 각 목표 아래에는 문제와 작업 내용을 한 묶음으로 쓰고, 수행 단계·실험·결과·남은 작업은 불릿에서 설명한다. 줄바꿈은 실제 개행으로 기록한다.
- 현재 변경·실행 결과로 확인한 사실을 우선하고, 커밋·이슈·작업 기록을 연결해 설명한다. 자료가 충돌하면 최신 검증 결과와 적용 상태를 확인한다. 미채택 실험을 적용 완료라고 쓰지 않는다.
- 정량 결과는 표본·비교 조건을 짧게 유지한다. 검색 성능을 답변 정확도로, 작은 실험을 전체 품질로 확대 해석하지 않는다.
- 신규 개발처럼 기존 결함이 없는 작업에는 `문제: ...가 필요함`처럼 확인된 필요성을 쓴다. 배경조차 없으면 `문제: 배경 정보 미확인`으로 두고 수행한 사실만 쓴다. 문제를 지어내지 않는다.
- 휴가·교육은 D의 `기타`에 간단히 적고 문제/작업 내용이나 진척도를 억지로 붙이지 않는다. Calendar 미조회는 `없음`이 아닌 `미확인`이다.

## 5. G열 — 차주 업무

진행 중 목표의 실제 잔여 작업, 관련 Todo, 확인된 후속 계획과 사용자 지정 내용을 §1의 기능·목표 단위로 묶는다. 계속하는 목표는 금주와 같은 이름을 쓰고, 차주에 할 실험·기획·구현·검증은 그 아래 불릿에 쓴다. 오래된 Todo 전체를 자동으로 차주 계획에 넣지 않는다. G열에도 날짜·진척도는 붙이지 않는다.

    1. 문서 기반 질의응답 개선
       - PR 리뷰 반영 및 통합 검증 마무리

    2. 증상 기반 장애 사례 탐색
       - 사례 묶음 기준 비교와 그래프 탐색 흐름 구체화

필요할 때만 상세 불릿을 추가하고, 여러 줄의 번호 블록 사이에는 빈 줄을 둔다. 한글 중심으로 쓰되 API, RCA, KDB 등 기술 명칭은 유지한다.
