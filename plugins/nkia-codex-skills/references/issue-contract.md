# 이슈 본문·Type·증빙 계약

신규 이슈와 명시적으로 전환을 요청한 이슈에 적용한다. 기존 이슈를 일괄 재작성하지 않는다.

## 본문

```markdown
[현재 문제]를 [기대 결과]로 바꾸는 작업.

## 1. 문제
- 발생 조건과 영향

## 2. 변경 내용
- 현재:
- 변경:

## 3. 완료 조건
- [ ] **AC-01** 관찰 가능한 결과
  - 증빙 예정: 해당 결과를 확인할 자료와 확인 방법
- [ ] **AC-02** 실패·경계·회귀 결과
  - 증빙 예정: 실패·경계·회귀 시나리오의 테스트 결과

## 4. 범위
- 포함:
- 제외:
```

- 변경 내용은 목적별로 작성한다. 필요한 기존 배경·참고 링크는 관련 절에 보존한다.
- 생성 시 각 AC 바로 아래에 `증빙 예정: 자료 종류·확인할 내용`을 들여쓴 불릿으로 작성한다. AC 문장 끝에는 증빙 안내를 붙이지 않는다. 가짜 링크·이미지·실행 결과나 `{{url}}` 같은 변수 placeholder는 만들지 않는다.
- 코드리뷰·PR 생성·merge 같은 제출 절차를 AC로 추가하지 않는다. 배포·문서 게시가 실제 결과물인 경우는 제외하지 않는다.
- Feature는 사용자 관점의 상위 결과, Task는 독립 실행·검증 가능한 결과를 쓴다. 부모·하위 연결을 유지한다.
- 담당자·사이클·상태와 저장 후 재조회 규칙은 creator의 공통 메타데이터 규칙을 따른다.

- 스토리 포인트 산정·입력·질문과 별도 AC 승인은 사용하지 않는다. `estimate`는 생성·갱신 요청에서 생략하고 기존 값은 보존한다. 신규 `[AC 요청]`·`[AC 확인]`은 붙이지 않고 기존 접미사를 승인 대기로 해석하지 않는다. AC·증빙 검증과 해당 작업의 설계 리뷰는 유지한다.

## Type 하나·프로젝트 하나

| Type | 주된 목적 |
|---|---|
| Bug | 기대 동작을 위반하는 오류 수정 |
| Feature | 새로운 사용자 기능·사용 시나리오 |
| Improvement | 기존 기능의 사용성·성능·품질 개선 |
| Refactoring | 외부 동작을 유지하는 내부 구조 개선 |
| Research | 학술적 지식·가설·새 방법론·논문 |
| Investigation | 제품·기술 선택을 위한 현황·대안·적용 가능성 조사 |
| Evaluation | 정해진 대상·기준으로 성능·적합성 측정·판정 |
| Build | 제품·AI 서비스 빌드·패키징·설치·배포·실행 인프라 |
| Documentation | 문서·가이드·설계서 자체가 결과물 |
| Task | 위 유형 외의 팀 운영·지원, 개인·팀 업무환경 구축 |

1. 생성·Type 변경 전에 팀과 워크스페이스의 이슈 라벨을 모든 페이지 조회한다.
2. 활성 라벨 중 부모 그룹이 정확히 `Type`인 라벨을 선택한다. 다른 그룹과 보관 라벨은 사용하지 않는다. 그룹 메타데이터가 없으면 추가 조회하고 추측하지 않는다.
3. 이름·부모 그룹·팀 적용 범위를 확인한 실제 ID로 Type 하나만 저장한다. ID를 스킬에 고정하지 않는다. 같은 이름 후보가 모호하거나 라벨이 없으면 필요한 필드만 한 번에 확인한다. 라벨을 임의 생성하지 않는다.
4. 버그를 고치면서 기능을 개선해도 주된 목적이 오류 수정이면 Bug다. 부수적인 문서·테스트·리팩터링으로 Type을 추가하지 않는다. 부모와 자식의 Type은 서로 다를 수 있다.
5. 데이터 작업은 고정 Type이 아니다. 새 데이터 기능이면 Feature, 기존 데이터 오류면 Bug, 측정이면 Evaluation처럼 결과로 결정한다. 정보 부족을 Task로 대체하지 않는다.
6. 제품·기능은 프로젝트, 상태·우선순위는 해당 필드로 관리한다. 옛 소문자 work/domain 라벨을 자동 부착하지 않는다. 기존 비-Type 라벨은 보존하고 명시적으로 요청한 유효한 추가 라벨만 반영한다.
7. 갱신 시 기존 Type을 선택한 하나로 교체하되 다른 라벨을 제거하지 않는다. 라벨 객체 자체를 삭제하지 않는다.
8. 프로젝트 하나를 실제 ID로 지정한다. 이니셔티브·제품·프로젝트 설명을 대조하고 동명 프로젝트를 이름이나 최근 수정일만으로 고르지 않는다. 미할당·옛 공통 프로젝트 폴백으로 저장하지 않는다.
9. 저장 후 재조회하여 정식 Type ID 하나, 프로젝트 ID, 담당자·사이클·상태를 검증한다. 불일치는 같은 이슈를 한 번 수정·재조회하고, 실패하면 중단한다. 불확실한 생성 응답은 조회로 확인하고 중복 생성하지 않는다.

## 증빙을 한눈에 확인

짧은 결과·로그는 AC 아래 증빙 불릿에 직접 적고 실제 출력은 들여쓴 코드 블록으로 표시한다. 장문 문서·로그·보고서는 해당 이슈의 Resources → Add document에 해당하는 Linear document로 저장하고 증빙 불릿에서 문서 URL을 링크한다. 고정 줄 수보다 이슈에서 한눈에 읽을 수 있는지를 기준으로 나눈다.

생성 시:

```markdown
- [ ] **AC-01** 필터 변경 시 해당 대상의 예측 결과가 표시된다.
  - 증빙 예정: 필터 전환 화면 캡처와 대상별 결과 비교 테스트
```

증빙 게이트에서는 예정된 자료를 수집·저장하고 내용을 확인한 뒤 **같은 하위 불릿**을 아래 실제 증빙으로 교체한다. 예정 안내와 실제 증빙을 중복해서 남기지 않는다. 여러 필수 자료 중 일부만 확보했다면 확보분은 `증빙:`, 미확보분은 `증빙 예정:`으로 구분하고 AC는 미체크로 둔다. 실패·접근 불가 시 예정 내용과 필요한 조치를 남기며 완료로 표시하지 않는다.

- 장문은 `save_document(issue=대상 이슈, title=제목, content=Markdown)`으로 생성한다. 기존 대응 문서가 있으면 ID로 갱신한다. `get_document`와 이슈의 documents를 재조회해 본문·소속·URL을 확인한다. 파일 attachment 업로드나 Add link로 대신하지 않는다.
- 짧은 출력은 실행한 명령·대상과 실제 결과를 증빙 불릿 아래 코드 블록에 넣는다. 이를 위해 별도 문서·파일을 만들지 않는다. 민감정보는 마스킹하고 요약·발췌와 원문을 구분한다.
- 이미지·바이너리 파일은 attachment를 사용한다. 문서 내부 상대 링크는 실제 Linear document URL로 연결한다. 이전 파일 첨부를 전환할 때는 새 document의 내용 확인과 본문·댓글 링크 교체 후 작업 소유의 대체 파일만 제거하고 PR·사용자 자료·이력은 보존한다.

```markdown
- [x] **AC-01** 필터 변경 시 해당 대상의 예측 결과가 표시된다.
  - 증빙: [화면 캡처](실제-asset-URL) · 필터 전환 테스트 8/8 PASS
```

- 실제 저장·접근·내용 확인 전에는 링크나 PASS 결과를 만들지 않고 체크하지 않는다. 체크 상태만으로 완료를 판정하지 않는다.
- 접근 확인은 작성자의 인증 성공만으로 판단하지 않는다. 개인 private 저장소는 팀 공유 증빙 경로로 사용하지 않으며, 대상 Linear 이슈의 팀원이 열람할 수 있는 document 또는 본문 증빙으로 제공한다.
- 화면 자체가 필요한 경우 대표 이미지를 해당 AC 아래에 inline 표시한다. 모든 이미지·긴 로그를 반복 삽입하지 않는다.
- 자료 제목은 `[AC-01, AC-02] 대상 — 방법 — 결과`로 저장한다. 여러 AC가 같은 장문 자료를 참조하면 document 하나를 공유한다.
- 별도 document·attachment로 저장한 증빙은 이슈당 최대 5개로 관리한다. 본문에 직접 적은 짧은 결과는 별도 자료 수에 넣지 않는다. PR/MR 링크는 제외하고, 이전 자료도 포함한다. 초과 시 기존 이력을 보존하는 합본 등을 준비하며 임의 삭제하지 않는다. 기존 형식에는 소급하지 않는다.
- 적용할 링크·요약·이미지·체크 변경을 미리보기로 제공한다. 이미 같은 적용을 승인받았다면 반복 질문하지 않는다.
- 원본 저장 성공 확인 후 최신 본문을 다시 읽고 대상 AC의 체크와 증빙 요약만 갱신한다. 동시 편집, 다른 AC, 기존 자료를 보존한다.
- 재검증에서는 최신 요약을 교체한다. 이전 증빙·실패·해소 이력은 검증 댓글에 보존한 뒤 교체하고 본문에 실행 이력을 계속 누적하지 않는다.
- validator는 AC 아래 짧은 실제 출력과 링크된 document·attachment 내용을 확인한다. 기존 `→ 결과물:`·inline 증빙도 읽되 새로 생성하지 않는다.
- `증빙 예정:`은 검증 계획이지 완료 근거가 아니다. 필수 예정 자료가 남아 있거나 실제 자료가 예정된 확인 내용을 충족하지 못하면 PASS하지 않는다. 기존 이슈를 명시적으로 전환할 때만 AC 끝의 증빙 안내를 하위 불릿으로 옮기거나, 같은 요구를 충족하는 실제 증빙 불릿이 이미 있으면 중복 안내만 제거한다. AC 조건·실제 자료·이력은 보존한다.
- 실패·미검증·접근 불가·증빙 부족 AC는 체크를 해제하고 이유를 기록한다. 제출 절차 AC는 원문·체크 상태를 보존하며 기능 검증에서 제외한다. 기능 AC가 0개이면 통과시키지 않는다.
- 코드 diff만으로 실행 결과를 증명하지 않는다. 민감정보를 제거하고 테스트 대상·방법·통과/실패 수·통과율·미실행을 구분한다.
